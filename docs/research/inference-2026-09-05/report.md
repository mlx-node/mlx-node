# Inference architecture on unified memory

Research date: 2026-09-05. Audience: mlx-node maintainers. Scope: model
integration, speculative decoding with paged KV, concurrent inference, SSD
persistence and macOS inference control flow. This is an engineering Markdown
report intended to live beside the implementation and its tests.

The [2026-09-06 follow-up](followup.md) records subsequent implementation,
measurements, rejected candidates and remaining work against PR revision `bbc3157c`.

## Decision

Keep the existing registry, immutable execution plan, shared scheduler and
family-owned tensor/cache implementations. Use one generic command envelope and default barrier dispatch; generate only
the concrete native export methods. Reduce host completion boundaries in mixed-row
sampling and deterministic speculative acceptance. Preserve the SSD cold tier.
Scheduled speculation and direct Metal backend migrations need separate measured
stages; their correctness prerequisites are recorded below.

The relevant performance constraint is synchronization as well as memory
bandwidth. Shared memory makes CPU/GPU data accessible without a discrete-device
copy, but a CPU read still depends on GPU completion. MLX explicitly distinguishes
lazy graph construction from evaluation and host access. [MLX lazy evaluation,
live 0.32.2 documentation](https://ml-explore.github.io/mlx/build/html/usage/lazy_evaluation.html).

The subsequent [full inference transfer audit](transfer-audit.md) identified and
removed normal-path KV staging in Qwen3 cache-hit prefill, redundant arithmetic
before host exports, vocabulary copies in sampled drafting, per-layer metadata
reductions and a duplicate PaddleOCR token round trip. It separately inventories
required output reads, synchronization and SSD staging. Its paired measurements
are in [validation.md](validation.md).

## What to retain and simplify

mlx-node already has a native-free family-data row and a typed loader binding,
with shared traits for chat, paging and speculation. `HybridSchedulerState`
owns admission, token budgets, preemption and SSD waits. The costly new work for
a model is its forward pass, batched tensor program and auxiliary-state lifecycle.
Those cannot be removed by a registry. A shared
`ModelCommand<FamilyCommand>` removes the per-family chat/stats enums, adapter
traits and conversion macro. Three inference-only families use its `Infallible`
extension directly; four define only their additional commands. Ordinary
chat-barrier dispatch is a backend trait default. Gemma4 and Muse retain the
owner-state hook that installs and reconciles their flat/paged lanes. Concrete
NAPI exports remain generated by the existing binding macro. See the updated
[extension guide](../../adding-a-model.md) and
[engine boundary](../../inference-architecture.md).

vLLM's runner separates stable active-request storage from temporary per-step
gathers and batches metadata updates. The transferable principle is stable request
ownership and fewer host/device handoffs. Its CUDA graphs and multiprocessing
topology are implementation choices, not requirements for our model thread.
[vLLM Model Runner V2 design](https://docs.vllm.ai/en/latest/design/model_runner_v2/).

## Speculation, paging and concurrency

Treat four frontiers separately: reserved capacity, optimistic verify writes,
accepted logical history, and completed device work. vLLM reserves lookahead but
caps prefix publication at finalized request tokens. Sliding eviction subtracts
in-flight tokens before deciding which blocks are no longer read.
[vLLM KV cache manager, pinned source](https://github.com/vllm-project/vllm/blob/874df9373dab532543a0229fb2f144f7c14093ae/vllm/v1/core/kv_cache_manager.py#L389-L562).

mlx-node already enforces reserve/write/commit/settle with sequence-bound,
noncopyable `VerifyTicket`s in
[the speculative cache transaction](../../../crates/mlx-core/src/engine/spec_paged.rs). A rejected attention suffix
rewinds a cursor; it does not erase physical KV. Recurrent GDN/Mamba state and
convolution history additionally require their owner's snapshot, tape replay or
checkpoint reconciliation. vLLM also tracks recurrent accepted positions
independently. [vLLM Mamba hybrid state](https://github.com/vllm-project/vllm/blob/874df9373dab532543a0229fb2f144f7c14093ae/vllm/v1/worker/gpu/model_states/mamba_hybrid.py#L89-L118).

| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| MTP              | Autoregressive draft executor updates positions and paged slot mappings across draft iterations.                                                                                     | Retain target hidden-state and recurrent commit semantics behind the MTP stepper.                                                      |

[DSpark speculator](https://github.com/vllm-project/vllm/blob/874df9373dab532543a0229fb2f144f7c14093ae/vllm/v1/worker/gpu/spec_decode/dspark/speculator.py#L40-L55).

vLLM combines prefill, decode and speculative verification using a token deficit
and a common budget. Rejection adjusts computed counts; the async scheduler uses
placeholders until token values arrive. This is safe because ownership and
in-flight state are explicit. [vLLM scheduler](https://github.com/vllm-project/vllm/blob/874df9373dab532543a0229fb2f144f7c14093ae/vllm/v1/core/sched/scheduler.py#L511-L520),
[async scheduler](https://github.com/vllm-project/vllm/blob/874df9373dab532543a0229fb2f144f7c14093ae/vllm/v1/core/sched/async_scheduler.py#L19-L69).

Our [speculative admission](../../../crates/mlx-core/src/engine/plan.rs)
correctly remains a barrier. Its documented
prerequisites are absent: multi-token row results, ragged batched verification,
per-owner speculative state and resumable drivers. A shared paged pool does not
make a model-owned draft cache concurrent. The dense paged-MTP epilogue is also
still a family fork; migrating it onto the existing shared epilogue should precede
reentrant execution.

Adaptive verification is a later optimization. vLLM ranks cumulative survival
probabilities and uses profiled step costs to select a verify budget. Metal needs
its own curves across batch size, context and cache pressure, measured in accepted
output tokens per second and latency. [vLLM adaptive verification](https://docs.vllm.ai/en/latest/features/speculative_decoding/adaptive_verification/).

## Unified memory and SSD

Current vLLM is not RAM-only: its native tiering offloader has a CPU primary tier
and optional filesystem, object-store or peer secondaries. The important hardware
distinction remains discrete GPU/pinned-CPU staging versus our unified resident
pool and SSD cold cache. Adding a permanent RAM duplicate would compete with
weights and active KV on this machine. [vLLM KV offloading guide](https://docs.vllm.ai/en/latest/features/kv_offloading_usage/).

Keep filesystem reads, checksum and identity validation off the model thread,
then install into reserved destinations and publish after successful completion
on the owning thread. The current `cold_cache.rs` split already does this.
oMLX's source records serial `mx.load` after worker-thread GPU contention, while
MTPLX defers immutable snapshot encoding to the model-owner idle lane. These are
reasons to preserve ownership, not evidence that all SSD work should be serialized.
[oMLX preload](https://github.com/jundot/omlx/blob/e467261edc786efd33b1e9023d5c4a827f8aa1c1/omlx/cache/paged_ssd_cache.py#L4217-L4226),
[MTPLX snapshot queue](https://github.com/youssofal/MTPLX/blob/13297feea79b60b957a6f374f21352087ac45dd1/mtplx/session_bank.py#L2134-L2156).

oMLX's DFlash engine delegates selected long-context work to its normal paged,
SSD-backed continuously batched engine. It is not evidence of shared scheduled
DFlash KV. [oMLX DFlash engine](https://github.com/jundot/omlx/blob/e467261edc786efd33b1e9023d5c4a827f8aa1c1/omlx/engine/dflash.py#L1-L9).

## Control-flow changes selected for implementation

Mixed scheduler waves currently build, submit and wait for each sampler
separately. Build the same row samplers in the same order, retaining each row's
penalties, forced reasoning token and random draw. Evaluate their roots together
before result handling. Keep the existing batched argmax for uniformly greedy
waves. mlx-vlm groups evaluation roots after per-row processing; MTPLX packs
token and accept decisions for one host boundary.
[mlx-vlm batch generation](https://github.com/Blaizzy/mlx-vlm/blob/d68a25e71e842e8924a54bb3d84d3a3b4d4a2ee1/mlx_vlm/generate/ar.py#L1206-L1315),
[MTPLX batched decisions](https://github.com/youssofal/MTPLX/blob/13297feea79b60b957a6f374f21352087ac45dd1/mtplx/batched_decode.py#L504-L519).

For greedy speculative acceptance with penalties, position i sees history plus
the draft prefix before i until the first rejection. All those deterministic
argmax graphs can be prepared before evaluating. Select the first mismatch or
the bonus afterward; later hypothetical rows are unused work. This is an inference
from the current algorithm, to be checked against a sequential oracle. Stochastic
acceptance retains its sequential residual/RNG behavior.

## Metal API applicability

| Mechanism                                     | Decision and requirements                                                                                                                                                             |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| MLX graph evaluation                          | Use now: combine completion boundaries before adding queues.                                                                                                                          |
| Shared events, fences, concurrent encoders    | Already used in vendored MLX `backend/metal/device.cpp`; preserve dependency tracking.                                                                                                |
| Residency sets / wired limits                 | Already integrated, macOS 15+. Manage a bounded working set; residency does not replace synchronization.                                                                              |
| Metal 4 command allocators / reusable buffers | macOS 26+, M1+. Prototype in the backend only after measuring encoding overhead. Retire allocator storage after GPU completion.                                                       |
| Metal 4 argument tables / barriers            | Part of that migration. Explicit resource hazards and binding lifetimes are required.                                                                                                 |
| Metal IO                                      | macOS 13+. Candidate for validated SSD payload reads into reserved buffers, with shared-event completion and a fallback. It provides no prefix identity, checksum or eviction policy. |
| Indirect command buffers                      | Candidate for stable-shape replay; measure encoder cost and maintain dynamic binding lifetimes.                                                                                       |
| Metal tensors / Shader ML / NAX               | Tensors are macOS 26+. Existing MLX NAX dispatch has stricter OS/architecture gates. Improve that dispatch before creating a competing tensor backend.                                |

Additional mechanisms worth measuring are placement-sparse buffers/heaps, which
can reserve virtual space separately from physical pages, and GPU counters for
separating CPU encoding from device execution. Sparse mappings still need block
ownership and completion-safe remapping; hardware support must be checked per
feature, independently of general Metal 4 availability. Shader pipeline/binary
caching affects compilation and cold startup, so it is a separate measurement
from steady decode. [Apple Metal feature tables](https://developer.apple.com/metal/feature-sets/),
[GPU counters](https://developer.apple.com/documentation/metal/gpu-counters-and-counter-sample-buffers).

Primary Apple sources: [Discover Metal 4, WWDC25](https://developer.apple.com/videos/play/wwdc2025/205/),
[Metal 4 core API](https://developer.apple.com/documentation/metal/understanding-the-metal-4-core-api),
[residency sets](https://developer.apple.com/documentation/metal/mtlresidencyset),

## Next-stage plan and gates

1. Consolidate dense paged-MTP finalization using the existing shared epilogue.
   Gate: mid-cycle cancellation/EOS, fresh/delta, GDN frontier and SSD restart
   parity for dense and MoE.
2. Introduce accepted-token spans in scheduler results, explicit committed versus
   computed counts, and per-owner draft/tape state. Preserve one-token AR as a
   conformance case. Gate: mixed acceptance, owner recycling, cancellation and
   allocation exhaustion without double rollback.
3. Make proposal/verify/commit resumable, add ragged verification, then admit
   scheduled speculation behind an opt-in. Gate: N=1 regression bound, N=2/4
   accepted-token throughput and p95 latency; mixed AR/speculative/prefill waves.
4. Port DFlash context and target paging independently. Gate: rejected suffix,
   sliding eviction, block boundaries, cold restore and exact warm provenance.
5. Measure Metal encoding and SSD restoration. Prototype Metal 4 or Metal IO only
   for a demonstrated bottleneck, using the same semantic gates and fallback.

Research stopped when each material question had primary source support or an
explicit prerequisite. No cross-runtime speedup percentages or unexecuted model
gates are claimed. Validation of the selected implementation is in
[measurements and checks](validation.md). The full Qwen3 workload improves
aggregate throughput by 2.68%, 5.84% and 13.32% at 2, 4 and 8 concurrent requests;
the single-request median regresses by 2.43%. Gemma4 DSpark preserves exact output
and acceptance counters but shows no resolved end-to-end gain in this workload.
